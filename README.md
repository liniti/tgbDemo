# Мониторинг заявок: демонстрационный прототип

Прототип читает заявки из JSON-экспорта и сохраняет состояние обработки в
SQLite. Для каждой новой заявки он отправляет уведомление в указанный
Telegram-чат и передаёт JSON во внутренний webhook. API закрытого кабинета здесь
не реализован: источник данных — подготовленный экспорт.

## Демонстрация

Из каталога проекта выполните:

```sh
python3 bot.py demo
```

Демонстрация использует временную базу и локальные имитации Telegram и
принимающей системы, не обращаясь к внешним сервисам. Внутри одного запуска
после первого прохода выполняется второй: уже доставленные заявки повторно не
отправляются. Каждый отдельный запуск `demo` создаёт новую временную базу.

## Запуск с экспортом и реальными адресатами

Экспорт должен быть JSON-массивом объектов с полями `id`, `title`, `amount`
(строка), `currency` и `created_at` (ISO 8601), например:

```json
[
  {
    "id": "req-1042",
    "title": "Настройка оборудования",
    "amount": "12500.00",
    "currency": "RUB",
    "created_at": "2026-11-16T18:30:00+03:00"
  }
]
```

Задайте переменные окружения и запустите обработку:

```sh
export TELEGRAM_BOT_TOKEN='токен-бота'
export TELEGRAM_CHAT_ID='id-чата-или-@имя'
export INTERNAL_WEBHOOK_URL='https://internal.example/api/requests'
python3 bot.py run --source examples/requests.json --db data.sqlite3 --once
```

`--once` обрабатывает доступный экспорт один раз. Без этого флага процесс
продолжает опрашивать источник; частоту задаёт `--interval <сек>` (по умолчанию
её определяет программа). SQLite-файл хранит прогресс между запусками. Для
периодической проверки используйте, например, `python3 bot.py run --source
examples/requests.json --db data.sqlite3 --interval 60`.

## Что получает каждая сторона

- Указанный через `TELEGRAM_CHAT_ID` чат получает обычный текст с названием,
  суммой, временем создания и ID заявки. Бот должен иметь право писать в этот
  чат.
- `INTERNAL_WEBHOOK_URL` получает исходный объект заявки как JSON методом POST,
  с заголовками `Content-Type: application/json` и `Idempotency-Key: <id>`.
  Запросы имеют таймаут; HTTP-перенаправления не выполняются.

Приёмнику следует хранить обработанные ключи `Idempotency-Key` с уникальным
ограничением и атомарно связывать запись ключа с созданием заявки. Если тот же
ключ придёт повторно, приёмник должен вернуть успешный HTTP-статус, не создавая
вторую запись. Это делает безопасными повторы webhook-запроса.

У Telegram Bot API для `sendMessage` нет ключа идемпотентности. Если Telegram
принял сообщение, но ответ потерялся или соединение оборвалось до подтверждения,
программа не может узнать, было ли оно доставлено. При повторной попытке
уведомление в этом редком случае может появиться в чате дважды.

## Ограничения

Это демонстрация обработки экспортированных данных и передачи уведомлений.
Формат реального экспорта, правила повторов и требования к внутренней системе
не известны.
